1. The pipeline at a glance

An Ethereum wallet turns a short, human-friendly secret into an address in a chain of small steps. Each step uses a different tool, because each step has a different job.

3. Six ideas that are easy to confuse

The pipeline mixes several kinds of operations. The table separates them and shows where each appears.

ConceptWhat it meansWhere it appearsKey property
Key generationCreating fresh secret randomness.The entropy behind the mnemonic, taken from a cryptographically secure random number generator.Not deterministic. Its only quality requirement is unpredictability.
Key derivationComputing keys deterministically from other secret data.Mnemonic → seed (PBKDF2), seed → master key and child keys (HMAC-SHA512, BIP-32).Same input, same output. One-way, so a child key does not reveal its parent (for hardened levels).
Public-key cryptographyA key pair whose two halves are linked by a one-way mathematical relation.secp256k1: Q = kG, and ECDSA signatures.Easy forward, hard backward (ECDLP). It has algebraic structure, which makes signatures possible.

ChecksumA little redundant data that detects accidental errors.The checksum bits in the last BIP-39 word, and the capitalisation pattern of EIP-55.Detects typos with high probability. It is not secret and gives no protection against an attacker.
EncodingChanging the representation of data without changing its information.Hexadecimal, 11-bit word indices, the 0x prefix, mixed-case letters.Fully reversible. It provides no secrecy and no integrity.

4. The role of each standard and primitive

BIP-39 — mnemonic sentence and seed

Turns 128 to 256 random bits into 12 to 24 words from a list of 2048 words, so a human can write down and re-type the secret. The last word also carries checksum bits taken from SHA-256, which catch most typos. The sentence is then stretched into a 512-bit seed with PBKDF2-HMAC-SHA512; an optional passphrase is added to the salt and produces a completely different wallet.

BIP-32 — hierarchical deterministic keys

Defines how one seed becomes a whole tree of keys. The master key and chain code are the two halves of HMAC-SHA512(“Bitcoin seed”, seed). Each child comes from HMAC-SHA512 over the parent chain code, the parent key and the child index. One backup therefore covers an unlimited number of keys.

BIP-44 — standard derivation paths

Gives a meaning to each level of the tree: m / purpose' / coin_type' / account' / change / address_index. The coin type for Ethereum is 60. Because every wallet follows the same layout, the same mnemonic reveals the same accounts in MetaMask, Rabby, Ledger and others. MetaMask increments the last level for new accounts, while Ledger Live increments the account level.

secp256k1 — elliptic-curve public-key cryptography

The curve y² = x³ + 7 over a 256-bit prime field. The public key is the private key multiplied by the base point G, the same operation as in Homework 1 but with 256-bit numbers. It is easy to compute and infeasible to invert, and it allows digital signatures: proving ownership of an address without revealing the private key.

Keccak-256 — the hash function

Compresses the 64-byte public key into a 32-byte digest. Ethereum keeps the last 20 bytes as the address. This gives a short fixed-size identifier, and the public key stays out of sight until the account signs its first transaction.

EIP-55 — mixed-case checksum

Hides a checksum in the capitalisation of the hex letters: a letter is upper-case when the matching hex digit of Keccak-256(lowercase address) is 8 or more. The address still contains the same 20 bytes, so old software keeps working, while new software can detect most typos.

5. Why not one single algorithm for everything?

Each step solves a different problem and needs different security properties. No single algorithm has all of them: a hash function cannot sign, an elliptic curve cannot compress arbitrary data, and a checksum cannot keep a secret.

What the system needsToolWhy that tool
A backup a person can write down and re-typeBIP-39Words are easier to copy than 256 random bits, and the checksum catches typos.
Many keys from a single secret, with one backupBIP-32A keyed hash (HMAC) gives pseudorandom child keys that are reproducible from the seed.
The same accounts in every walletBIP-44It is only a convention for the path, but interoperability depends on it.
Signatures and a public/private relationsecp256k1Only public-key cryptography lets anyone verify a signature while the signing key stays secret.
A short fixed-size identifierKeccak-256A hash maps the public key to 20 bytes and removes its algebraic structure.
Catching a mistyped addressEIP-55It adds about 15 check bits without changing the address format.

The split is also practical: a primitive can be replaced independently of the others, and the same BIP-39 and BIP-32 machinery serves many blockchains, with only the last steps (curve, hash, address format) changing.

6. Historical context

Highlighted entries are the ones requested by the assignment; the others give context.

    RSA introduces practical public-key cryptography, based on the difficulty of factoring.
  • 2000
    The secp256k1 curve is specified in the SEC 2 standard.
  • 2001
    SHA-2 is standardised (FIPS 180-2), including SHA-256 and SHA-512. Both are still used inside BIP-39 and BIP-32.
  • 2009
    Bitcoin starts, using secp256k1 and SHA-256.
  • 2012
    BIP-32 defines hierarchical deterministic wallets. In the same year NIST selects Keccak as the winner of the SHA-3 competition.
  • 2013
    BIP-39 defines mnemonic codes for deterministic wallets.
  • 2014
    BIP-44 defines multi-account hierarchical deterministic wallets.
  • 2015
    SHA-3 is standardised by NIST (FIPS 202), based on Keccak. Ethereum launches in the same year, using the original Keccak-256.
  • 2016
    EIP-55 introduces the mixed-case checksum for Ethereum addresses.

7. SHA-2 / SHA-512 versus Keccak / SHA-3

Both are cryptographic hash functions, but they are built differently. SHA-2 is a Merkle–Damgård design. Keccak is a sponge construction, and it is the design selected for SHA-3.

SHA-2 (SHA-256, SHA-512)Keccak / SHA-3
DesignMerkle–Damgård with a compression functionSponge construction around the Keccak-f[1600] permutation
StandardFIPS 180-2, 2001FIPS 202, 2015
Length-extension attackPossible on plain SHA-256 and SHA-512Not possible
Role in this pipelineSHA-256 for the BIP-39 checksum; SHA-512 inside PBKDF2 (BIP-39 seed) and HMAC (BIP-32)Keccak-256 for the address and for the EIP-55 checksum

Keccak-256 is not SHA3-256. They use the same permutation and the same parameters, but NIST added a domain-separation suffix when it standardised SHA-3: SHA3-256 appends the bits 01 to the message before the usual padding, so its first padding byte is 0x06, while the original Keccak uses 0x01. Ethereum adopted Keccak-256 before the standard was finalised and kept it. The two functions therefore give completely different digests for the same input, and software that uses a standard SHA3-256 by mistake produces wrong Ethereum addresses.

8. Statistical properties

A good hash function or key-derivation function should make its output look random, even for very regular inputs. Below we measure this on the real primitives. The experiments start automatically with default sizes and use fresh random numbers each time you run them. Passing simple statistical tests is a necessary sign of quality, not a proof of security: these tests can only reveal gross bias.

8.1 Hash functions: avalanche effect and uniformity

Avalanche: flip one random bit of a random 32-byte message and count how many digest bits change (ideal: half of them). Uniformity: hash the counters 0, 1, 2, ... and check whether every output bit is 1 about half of the time, whether all 256 byte values are equally frequent (chi-square), and whether the output is correlated with the input counter.

Right: fraction of 1s for every output bit; the dashed lines mark ±3 standard deviations around 0.5. The “worst bit” column is the largest deviation measured in standard deviations; values up to about 4 are normal when hundreds of bits are tested. A chi-square statistic close to 255 (the degrees of freedom) and a correlation close to 0 are the expected results.

8.2 The whole pipeline: from entropy and indices to addresses

Sequential indices: the addresses m/44'/60'/0'/0/i for i = 0, 1, 2, ... of the seed derived above. The inputs differ by 1, and the outputs should still look unrelated. Entropy avalanche: flip one bit of a random 128-bit entropy and recompute everything (mnemonic, seed, address). The mnemonic is only an encoding, so it should change very little, while the seed and the address should change completely.

Computing...

An address has 160 bits, so a random function changes about 80 of them (standard deviation about 6.3). The seed has 512 bits, so about 256. A 12-word mnemonic changes only one or two words after a one-bit change: encoding preserves locality, hashing destroys it.

8.3 EIP-55: how many errors does the checksum catch?

We generate random addresses, check how many letters each one has (every letter carries one checksum bit), and then introduce one random wrong character in each address and see how many wrong addresses still pass the check.

Computing...

Each hex character is a letter with probability 6/16, so an address has on average 15 letters, that is 15 check bits. A random typo passes with probability about 2−L, where L is the number of letters; averaged over all addresses this is (13/16)40, about 0.0247 %. Addresses with few letters are protected less. In about 1 address out of 2000 all the letters end up with the same case; such an address, and a typo that produces one, looks like an address without checksum, which is why the last two rows are counted separately.

8.4 What the statistics tell us

  • Hash functions look alike statistically. Keccak-256, SHA3-256, SHA-256 and SHA-512 all show about 50 % avalanche and uniform outputs. Statistics cannot tell Keccak-256 from SHA3-256: they differ in structure and padding, not in randomness.
  • Derivation hides regular inputs. Consecutive indices and one-bit changes of the entropy give outputs that look unrelated, because BIP-32 and BIP-39 rely on HMAC-SHA512 and PBKDF2-HMAC-SHA512.
  • Encoding is not hashing. The BIP-39 words change locally, which is exactly what makes them easy to copy; the randomness only appears after PBKDF2.
  • Public-key maps are different. k → kG does not aim for avalanche: (k + 1)G = kG + G, as seen in Homework 1. This algebraic structure is needed for signatures, and it is the reason a hash is applied to the public key before it becomes an address.
  • A checksum is a statistical safety net. EIP-55 gives about 15 bits of error detection per address, enough to catch about 99.9 % of random single-character typos, but not all of them, and it does nothing against deliberate substitution.
